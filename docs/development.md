# 開発ルール(Development)

本ドキュメントでは、本プロジェクトにおける基本的な開発ルールを定義します。

## 🎯 開発の基本方針

- シンプルな実装を優先する
- 可読性を重視する
- 小さく変更して頻繁にコミットする
- 動作確認を必ず行う

---

## 🔧 開発の流れ

基本的な開発フローは以下の通りです。

1. Issueを作成
2. 最新の`develop`ブランチを取得
3. featureブランチを作成
4. 実装・修正
5. 動作確認
6. コミット
7. Pull Requestを作成

※詳細は[Git運用](./git-workflow.md)を参照

---

## 🧪 動作確認

開発後は必ず以下を確認してください。

- アプリが正常に起動する
- 追加・修正した機能が期待通り動作する
- エラーが発生していない

---

## 🗄 データベース変更

モデル変更を行った場合は、マイグレーションを実行してください。

```bash
docker compose exec app python manage.py makemigrations
docker compose exec app python manage.py migrate
```

---

## ✍️ コーディングルール

- Djangoの標準的な構成に従う
- 変数・関数名は意味の分かる名前にする
- 不要なコメントは書かない
- 必要な箇所には適切にコメントを書く

---

## 📦 コミットルール

コミットメッセージは以下の形式を推奨します。

- ✨ feat: 新機能追加
- 🐛 fix: バグ修正
- ♻️ refactor: リファクタリング
- 📝 docs: ドキュメント更新
- 🎨 style: コードスタイル修正(動作に影響なし)
- 🚀 perf: パフォーマンス改善
- ✅ test: テスト追加・修正
- 🔧 chore: ビルド・設定変更


---

## 🔍 Pull Request前チェック

PR作成前に以下を確認してください。

- [ ] アプリが正常に動作する
- [ ] 不要なコードが含まれていない
- [ ] マイグレーションが必要な場合は実行済み
- [ ] ドキュメント更新が必要な場合は対応済み

## 🎫 Issue運用

本プロジェクトでは、基本的にIssueベースで開発を行います。

- 作業前にIssueを作成する
- 1つのIssueにつき1つの目的で作成する
- Issue番号をコミット・PRに紐付ける

## 🔗 IssueとPull Requestの連携

Pull Requestは必ず関連するIssueと紐付けてください。

RPの説明欄に以下を記載します。

```md
closes #<Issue番号>
``
